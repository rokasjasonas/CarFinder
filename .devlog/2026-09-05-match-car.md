# 2026-09-05 — Match car: ask/suggest loop + ranking integrity

**Tags:** kotlin, compose-multiplatform, ranking, android

The flagship feature: after swiping through listings, a "Get my match car" button
shows the single best car with as much info as possible (engine, size, price,
running costs) plus an ask/suggest loop where every answer sharpens the pick.
Building it surfaced a ranking problem worth its own war story: "best match"
kept preferring *priceless* listings over priced, well-documented ones.

### Problem

The user asked for (original brief): *show cars, learn from every like/dislike,
a "Get my match car" button showing as much info as possible — engine, size,
price, etc. Ask, suggest.*

Two sub-problems emerged during verification:

1. **Match quality.** The engine's score is a weighted blend of the user's
   quiz answers (budget, usage, power, …). Listings with `priceEur == null`
   ("Price on request") silently skipped the budget component, and because
   scores are renormalized over present components only, a priceless 2023
   Volvo XC60 out-scored a priced, under-budget minivan — the user's #1
   criterion was literally not being checked for the top pick.
2. **Honest display.** The generalized documentation tiebreak (pick the
   better-documented car within a 3-point window) could pick a car whose
   score is *lower* than the runner-up's, so the UI read "Your match car · 69%
   match … Next best · 72%" — indistinguishable from a bug.

### What didn't work

- **Completeness-only tiebreak, first attempt.** Renamed
  `PRICE_TIEBREAK_POINTS` → `TIEBREAK_WINDOW_POINTS = 3` and made the tiebreak
  key count *documented fields* (price, mileage, year, body, fuel, power,
  engine, gearbox). Verified on device → regression: the priceless XC60
  ("Price on request", 75%) displaced the priced Insignia (78%) because it had
  more non-null fields. Lesson: documentation quality must not outrank price
  presence — the two are different tiers.
- **Lexicographic tiebreak (price trumps fields).** `tiebreakKey = price?8:0 +
  documentedFields`. Correct within the window, but the XC60 beat priced cars
  by *more* than 3 points, so the window never fired. Patching the symptom
  with a wider window would just move the cliff.
- **Widening the window.** Same flaw — any fixed window is a cliff somewhere
  else. The root cause had to be fixed in the score itself.

### Solution

Two changes in `shared/src/commonMain/kotlin/lt/carfinder/engine/MatchEngine.kt`:

1. **Budget partial credit for unknown price.** `budget()` used to `return
   null` for `priceEur == null` (component skipped, renormalized away). It now
   returns partial credit, mirroring the existing precedent where an unknown
   body type earns 0.5 in `usage()`:

```kotlin
// budget component — unknown price gets partial credit instead of a free pass
if (car.priceEur == null) return Component("budget", "Budget", 0.5f, 2f)
```

   With weight 2 in a 13.5-weight pool this costs a priceless car ~7.4 points
   versus a priced one — enough that priced cars win naturally and the 3-point
   tiebreak only arbitrates near-ties.

2. **Explain displaced runner-ups in the UI**
   (`shared/src/commonMain/kotlin/lt/carfinder/ui/MatchCarScreen.kt`). When the
   runner-up out-scores the pick (i.e. it lost the tiebreak), show *why*
   instead of a confusing higher %:

```kotlin
val detail = if (ru.score > best.top.score) {
    if (ru.car.priceEur == null) "no price listed — can't check against your budget"
    else "listing is missing key details"
} else " · ${ru.score}%"
```

The ask/suggest side: `BestMatch(top, runnerUp, confidence, ask, suggestions)`;
confidence = 50% answered questions (Refine.sharpness) + 25% swipe learning
(tasteW/MAX_TASTE_WEIGHT) + 25% top-vs-runner-up separation; the ask card
shows one question at a time (body → power bands → mileage bands → year bands
→ brands) while confidence < 85, each answer feeding back through
`answerAsk()` = `answerRefine()`.

Verified on the emulator end-to-end (screenshots below): priced Chrysler
Pacifica wins at 75% with the full spec grid — Price €11 999, Year 2017,
Mileage 108 000 km, Size MPV/Van, Fuel Petrol, Power 295 hp, Engine 217 kW,
Gearbox Automatic, Running costs ~2 082 €/yr — and the Next-best chip explains
the displaced priceless XC60. 29 host tests green
(`./gradlew :shared:testAndroidHostTest`).

### Tips & gotchas

- **Unknown ≠ neutral.** Whenever a scoring component is skipped for missing
  data, the car gets a *free pass* on that criterion after renormalization.
  Partial credit (0.5) beats skipping almost every time.
- **Compose chips expand touch targets to 48×48dp.** A swipe gesture starting
  at (540,1600) grazed the Skip chip's expanded target and silently fired it.
  Start test swipes away from chip rows.
- **`MatchEngineTest.kt` holds two classes** (`MatchEngineTest`, then
  `SitesTest`); engine tests must go inside the first one or they silently
  become Sites tests.
- **`export A=x B=$A/...` on one line expands `$A` before the first
  assignment** — shell exports each need their own line in build scripts.
- The live harvester mutates the pool between screenshots (12s rounds), so
  match %/confidence shift between runs — compare structure, not numbers.
- One stale autogidas record (Insignia `0139838976`) parses with almost no
  fields; the tiebreak demotes it instead of hard-failing on thin data.
